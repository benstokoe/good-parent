# Adopt Convex + Clerk, and add web as a first-class target platform

**Note:** the web-as-a-target-platform portion of this decision is superseded by `docs/adr/0007` — web has been dropped as a target and the app is now iOS/Android only. The Convex + Clerk portion (accounts, cross-device sync) is unaffected and remains current.

GoodParent's product commitments (`PRODUCT.md`) originally stated the app is local-only with no server backend and no accounts, consistent with a privacy-first, single-user posture inherited from the SwiftUI version. During Expo scaffolding, we decided to reverse this: persistence moves to Convex, and accounts move to real sign-in via Clerk (`ConvexProviderWithClerk` — Convex validates Clerk-issued JWTs, configured in `convex/auth.config.ts`), so a parent's Check-Ins, Milestones, and Journal survive a lost or replaced phone and carry across devices. Web becomes a first-class target platform alongside iOS/Android for the same reason: an account is only worth having if it's usable from more than one client.

We considered keeping local-only storage (SQLite/WatermelonDB, as originally scoped) and treating any future sync need as a later, opt-in layer. We rejected deferring it: this app is meant for an eventual App Store/Play Store release to other parents (`PRODUCT.md`), and losing years of Check-Ins and Milestones to a lost device would be a bad first impression to design around retroactively. Building on Convex+Clerk from the start avoids a painful local-to-cloud data migration later, at the cost of the app now requiring connectivity and an account where it previously required neither — a real trade-off against the "private, local, no accounts" framing this project started with.

This is a genuine reversal of a documented commitment, not a refinement of it. A future reader of `PRODUCT.md`'s original privacy language should not assume it's still accurate — it was rewritten alongside this decision.

**Consequences / follow-on decisions:**
- **Offline behavior is explicitly deferred.** Convex is online-first (WebSocket-synced queries/mutations); the app currently requires connectivity. This is a known gap, not an oversight — see the note in `PRODUCT.md`'s Operating Context. Revisit if Panic Button/Burn usage during connectivity gaps turns out to matter in practice.
- **Auth in Expo Go:** Clerk's *custom flows* (own screens against Clerk's hooks) work in Expo Go; Clerk's native prebuilt UI components require a dev client. Use custom flows to keep the project testable in Expo Go.
- **Panic Button conversation content is not automatically covered by this decision.** `docs/adr/0004` leaves on-device-vs-cloud AI processing for the Panic Button an open question specifically because that content is the most sensitive in the app. Do not assume Convex is the answer to that ADR's question — it must still be raised with the user before Panic Button conversation data is synced anywhere.
- **Web gets its own layout**, not a scaled-up mobile view — see the Layout section of `DESIGN.md` and its note there.
